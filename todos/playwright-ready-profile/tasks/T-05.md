# T-05 — Publikacja profili i krótka instrukcja użytkownika

## Cel i powiązanie

Opublikować nowy kontrakt narzędzia w profilach oraz zwięzłą, prawdziwą instrukcję minimalnego workflow. Realizuje R-01–R-06 z [planu](../plan.md#wymagania), bez dodawania kolejnych funkcji.

## Wymagany kontekst

Przeczytaj decyzje D-07 i C-01–C-06 w [planie](../plan.md). Kolejka i dowody wcześniejszych zadań są jedynym źródłem informacji o tym, co rzeczywiście wykonano; nie przedstawiaj oczekiwań jako wyników.

## Miejsca zmian

- Istniejące: `README.md`, `mcp/README.md`, `mcp/images/playwright/README.md`, `mcp/images/playwright/tests/README.md`, `profiles/wordpress/README.md`, `skills/wcag-audit/SKILL.md`, `docs/testing.md`, `docs/profile-management.md` tylko w miejscach opisujących ten runtime.

- Ewentualne pozostałe komunikaty Playwright w `core/rust/src/profile_management/installation.rs`, `scoped.rs` wyłącznie gdy wymagają korekty użytkowego opisu; nie dodawaj nowego zachowania.

## Kontrakt implementacji

Krótka instrukcja ma zawierać tylko normalne czynności użytkownika:

1. instalacja profilu istniejącym `make install CLIENT=... PROFILE=... PROJECT=...`;
2. ręczny `docker build --tag ai-profiles-playwright:0.2.0 .ai-profiles/wybrany-klient/mcp/playwright` w projekcie (dla WordPress użyj istniejących placeholderów renderowanych przez instalator, nie dosłownego katalogu `wybrany-klient`);
3. opcjonalne utworzenie `.private/playwright-basic-auth.json` z trzema zaakceptowanymi polami i prywatnymi prawami;
4. restart klienta i jego natywne zgody, jeśli wymagane przez aplikację.

Nie każ wykonywać mkdir, edytować Compose/local.json ani ustawiać sieci w standardowym scenariuszu. Nie twierdź, że Docker build utworzy reports hosta. Wyjaśnij jednym zdaniem, że dostarczony launcher wykonuje przygotowanie narzędzia automatycznie, a VPN/host pozostają poza zakresem.

Zachowaj osobną krótką sekcję wyjątków: niestandardowy CA, jawne stare nadpisania, brak obrazu, brak uprawnień, błędny origin/credentials i konieczny restart. Jawne nazwy plików używają reports; nie obiecuj naprawy upstreamowego `screenshot.png` w RO root.

Wersje profili ustaw na React 3.0.0 i WordPress 2.0.0. Innych profili nie bumpuj. Instrukcja migracji: update wybranego klienta, build 0.2.0, restart; stare obrazy/raporty i frozen legacy pozostają. Istniejące local.json może nadal wymuszać dawną sieć lub komendę — nie usuwaj go automatycznie i nie obiecuj nowego zachowania przy świadomym nadpisaniu.

## Zakres

Dozwolone: dokumentacja, wersje i spójność komunikatów. To zadanie publikacyjne, nie końcowa faza pisania testów. Wszystkie nowe zachowania muszą już mieć dowody swoich zadań. Bez nowej biblioteki, zmiany CLI, restrukturyzacji dokumentacji i prac nad innymi profilami.

## Procedura

1. Przejrzyj dotychczasowe dowody w planie i wyprowadź checklistę treści z wymagań. Dla samej dokumentacji/metadanych nie wymuszaj RED ani nie psuj implementacji.
2. Wprowadź zwięzłe instrukcje i jawny bump metadanych. Sprawdź zgodność tagów, ścieżek dla wszystkich klientów, renderowanych placeholderów oraz rozróżnienie „konfiguracja przygotowana”/„połączenie potwierdzone”.
3. Sprawdź odnośniki i usuń wyłącznie nieaktualne instrukcje dotyczące obecnego setupu, nie historyczne świadectwa. Nie zmieniaj zastanej polityki testowej.
4. Uruchom bramkę całego publikowanego zakresu; zapisz rzeczywisty wynik i ograniczenia. Nie przypisuj weryfikacji prawdziwemu VPN, Docker Desktop, arm64 lub realnej sesji klienta, jeśli takich sprawdzeń nie było.

## Weryfikacja i oczekiwane wyniki

- Kontrola treści: standardowy workflow nie wymaga mkdir/local.json/Compose edits/hostowego Node, Basic Auth jest opcjonalny, origin wymagany i ograniczony, secrets poza raportami/Gitem, brak automatyzacji VPN lub hosta.
- Kontrola linków/placeholderów: pliki źródłowe istnieją; WordPress używa `{{AI_PROFILE_MCP}}`, `{{AI_PROFILE_LOCAL}}`, `{{AI_PROFILE_CLIENT}}` tam, gdzie wymagany jest rendering; końcowa instrukcja zainstalowana nie zawiera nierozwiniętych placeholderów.
- Metadane: tylko dwa wskazane profile zmieniają wersję; obraz 0.2.0 i komunikaty są zgodne. `make validate` jest częścią bramki `make test-all`; nie powtarzaj go wyłącznie dla formalności.
- Polecenia z root: `make test-all`; przy zachowaniu zakresu eksportera potwierdź istniejący dowód `bash tests/vm/check.sh` z T-01, ponów go tylko jeżeli w tym zadaniu zmienisz orkiestrację.
- Testy realnego adaptera dotyczą standardowego workflow w VM. Stwierdzenie „każdy klient otrzymał poprawną konfigurację” musi opierać się na testach lifecycle, nie na udawanej nawigacji w trzech rzeczywistych aplikacjach.

## Kryteria ukończenia

Instrukcja odpowiada zaimplementowanemu minimalnemu workflow, wersje i kompatybilność są jawne, linki/rendering poprawne, wymagana bramka przeszła. Wszystkie poprzednie zadania pozostają zaakceptowane; brak niewykonanych wymaganych kontroli.

## Warunki zatrzymania

Sprzeczność dokumentacji z zachowaniem, brak dowodów poprzedniego zadania, nieoczekiwana regresja lub niedostępna wymagana weryfikacja. Nie rozszerzaj zakresu i nie oznaczaj wydania jako gotowego na podstawie samego przeglądu dokumentacji.
