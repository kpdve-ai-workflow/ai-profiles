# T-03 — Istniejące nazwy hostów i DNS dostępne w kontenerze

## Cel i powiązanie

Playwright widzi lokalną aplikację i istniejący resolver hosta bez ręcznego wskazywania sieci DDEV. Realizuje R-04 oraz sieciową część R-01 z [planu](../plan.md#wymagania). Nie jest to automatyzacja ani naprawa VPN.

## Wymagany kontekst

Wiążą C-04 i C-06 w [kontraktach](../plan.md#kontrakty). Źródło oczekiwania: wymaganie użytkownika oraz dokumentacja Docker host networking wskazana w planie. Przeczytaj `AGENTS.md`, `docs/testing.md`, wczytaj `test-gap-discovery`.

## Miejsca zmian

- Istniejące: `mcp/images/playwright/compose.yaml`, `mcp/images/playwright/tests/run.sh`, `smoke.cjs`, `README.md`; `core/src/playwright/runtime.rs`, `core/src/profile_management/payload.rs`, `scoped.rs` dla automatycznego wyboru/dystrybucji host overlay.
- Dodaj: `mcp/images/playwright/compose.host.yaml` — wyłącznie wąskie mounty RO resolvera i hosts dla trybu host.
- Dodaj: `mcp/images/playwright/tests/dns-fixture.cjs` — mały syntetyczny DNS uruchamiany wyłącznie w VM, bez nowej zależności npm.
- Ewentualna korekta testów składania konfiguracji w `core/tests/playwright.rs`; dokumentacja runtime w `mcp/images/playwright/README.md`, `mcp/README.md`.

## Kontrakt implementacji

Domyślne Compose ma `network_mode: ${AI_PROFILE_PLAYWRIGHT_NETWORK:-host}`. Launcher automatycznie dodaje `compose.host.yaml` z wąskimi mountami RO plików `/etc/hosts` i `/etc/resolv.conf`, `create_host_path: false`, tylko dla domyślnego/jawnego trybu host, jak w C-04. Projekt nadal RO, reports RW. Utrzymaj jawne nadpisanie sieci, lecz nie nazywaj bridge równoważnym hostowi. Jawny bridge nie otrzymuje automatycznie hostowego resolvera loopback. Host overlay musi trafić do payloadu i listy rozpoznawanych referencji renderera.

Nie dodawaj kodu do wykrywania VPN, odczytu jego konfiguracji, wyboru interfejsu, włączania tunelu, DNS lub tras. To samo narzędzie korzysta z aktualnie gotowego środowiska. Docker Desktop/remote Engine nie są nowym wspieranym zakresem tego zadania.

## Zakres

Dozwolona wyłącznie konfiguracja sieci/DNS samego kontenera i testy w VM. Nie zmieniaj hostowego `/etc`, NetworkManager, systemd-resolved, firewalla, Incus ani firmowego VPN; nie dodawaj uprzywilejowanego kontenera i nie montuj socketu Docker.

## Procedura

1. Zdefiniuj oracle: kontener widzi istniejące mapowania nazw i konfigurację resolvera hosta przez wąskie RO mounty, a lokalny HTTP pozostaje dostępny bez env wybierającego sieć. Samo domyślne host networking wprowadzono już w T-02; jego test może być GREEN od początku i nie należy wymuszać regresji.
2. Dodaj test loopback bez manualnego local.json dla sieci. Sprawdź też realne mounty RO i zgodność odczytanych plików z hostem VM.
3. Dodaj izolowany DNS fixture odpowiadający wyłącznie dla `app.corp.test` adresem testowego serwera. Można uruchomić go w osobnym jednorazowym kontenerze z host networking, na `127.203.77.53:53`, bez mountów RW hosta. To adres loopback fixture, nie konfiguracja firmowego DNS. Testowy overlay montuje syntetyczny resolv.conf z tym nameserverem do kontenera Playwright. Nie zmieniaj systemowego resolv.conf VM. Prywatna domena ma rzeczywiście zadziałać w Chromium. W scenariuszu domyślnego uruchomienia bez testowego overlay nadal porównaj mounty z rzeczywistymi plikami hosta VM.
4. Uruchom `make test` i `make test-playwright` przed dodaniem produkcyjnego host overlay. RED ma wykazać brak automatycznego overlay i wymaganych RO mountów istniejących plików hosta; nie brak działającego DNS fixture. Test localhost chroni już istniejące zachowanie. Zajęty port/brak VM klasyfikuj jako problem infrastruktury.
5. Wprowadź konfigurację C-04, zachowaj ograniczenia mountów i cleanup wyłącznie własnych kontenerów fixture; wykonaj bramkę.

## Weryfikacja i oczekiwane wyniki

- Rzeczywiste Docker/MCP/Chromium w VM; brak mockowania sieci będącej przedmiotem testu.
- Błędny wariant bridge wykrywa brak treści unikatowej dla hostowego loopback HTTP. Błędny publiczny lub Docker DNS wykrywa nieudana nawigacja do syntetycznej prywatnej domeny; fixture musi rejestrować zapytanie DNS. Brak mountu hostowego hosts/resolv wykrywa porównanie zawartości i flag RO w rzeczywistym kontenerze.
- Test zachowuje odmowę zapisu poza reports. Nie zależy od Internetu do weryfikacji domeny `.test`.
- Polecenia: RED `make test` i `make test-playwright`, akceptacja `make test-all`. Nie dodawaj scenariusza prawdziwego VPN do wymaganych bramek. Dowody opisz jako „syntetyczny resolver + host networking”, nie „firmowy VPN zweryfikowany”.

## Kryteria ukończenia

Domyślna konfiguracja dociera do loopback bez nadpisań, prywatny DNS działa w prawdziwym Chromium na kontrolowanej fixture, read-only mounty są potwierdzone, a bramka przeszła. Host nie został rekonfigurowany.

## Warunki zatrzymania

Potrzeba zmiany sieci/plików hosta, konflikt portu DNS fixture, brak wymaganych uprawnień/VM lub rozbieżność zachowania Docker z przyjętym kontraktem. Nie stosuj publicznego DNS jako fallbacku, nie dodawaj skipów i nie konfiguruj VPN.
