# T-02 — Dostarczany launcher i opcjonalny Basic Auth bez local.json

## Cel i powiązanie

Po instalacji profilu i ręcznym buildzie MCP działa bez `mkdir`, edycji Compose lub `local.json`. Opcjonalne uwierzytelnienie wymaga jednego pliku. Realizuje R-01, R-02, R-03 i R-06 z [planu](../plan.md#wymagania).

## Wymagany kontekst

Wiążą C-01, C-02, C-03, C-06 i D-02/D-03 w [planie](../plan.md). Przeczytaj politykę testową i wczytaj `test-gap-discovery`; przy kodzie Rust również skill `rust`, jeśli dostępny. Nie zmieniaj schematu istniejącego helpera Basic Auth.

## Miejsca zmian

- Dodaj: `core/rust/src/playwright.rs`, `core/rust/src/playwright/runtime.rs`, `core/rust/src/bin/playwright-launcher.rs`, `core/rust/tests/playwright.rs`.
- Istniejące: `core/rust/src/lib.rs`, `profile_management/payload.rs`, `profile_management/scoped.rs`, `mcp/servers/playwright.json`, `mcp/example.json`, `mcp/images/playwright/compose.yaml`.
- Testy: `core/rust/tests/lifecycle.rs` — fixture `playwright_source`, testy dystrybucji i aktualizacji; `mcp/images/playwright/tests/run.sh`, `smoke.cjs`, `create-fixtures.cjs`, `basic-auth.test.cjs`.
- Istniejący helper `mcp/images/playwright/basic-auth.cjs` i `entrypoint.sh` tylko w razie konieczności wynikającej z testu; ich obecne walidacje muszą pozostać.
- Opcjonalny przykład bez sekretów: `mcp/images/playwright/basic-auth.example.json`, dodany jawnie do payloadu. Nie jest prawdziwym credentials ani automatycznie wczytywanym plikiem.

## Kontrakt implementacji

Wykonaj C-01 i C-03. Rejestr wybiera natywny launcher, a adapter nadal wykonuje wspólne rozwiązywanie konfiguracji. Nie dodawaj specjalnego przetwarzania Playwright do ogólnego adaptera. Stdout launchera zawiera tylko strumień MCP.

W tym zadaniu ustaw również domyślną sieć Compose na `${AI_PROFILE_PLAYWRIGHT_NETWORK:-host}`, zachowując jawne nadpisanie. Jest to konieczne, aby czysty workflow z lokalnym HTTP nie wymagał ręcznego wyboru sieci; dodatkowe udostępnienie istniejących plików hosts/resolvera należy do T-03. Ta jedna zmiana konfiguruje kontener, nie VPN ani hosta.

Domyślny credentials jest współdzielonym plikiem projektu, ale rejestr/payload każdego klienta nadal pozostają oddzielne. Automatycznie wybieraj istniejące rozszerzenia Basic Auth/storage state; ręczna lista Compose pozostaje zgodna. Wykryty credentials nie jest wczytywany do manifestu lub logów.

Regułę Git dodawaj w fazie przygotowania/zapisu klienta tak, aby błędny typ `.gitignore` został wykryty przed nadpisaniem zarządzanych plików. Nie hashować całego `.gitignore`, nie usuwać reguły przy uninstall. Nie twórz prywatnego pliku za użytkownika i nie zmieniaj praw istniejącego pliku.

## Zakres

Dozwolone: natywny launcher, dystrybucja, przygotowanie reports, domyślne host networking kontenera, automatyczne podłączenie istniejących wejść i wąska reguła Git. Poza zakresem: mounty hosts/resolvera (T-03), wykrywanie CA (T-04), automatyczny Docker build/pull, hostowy Node/Python/jq, zmiana niezależności klientów i zamrożonego payloadu legacy.

## Procedura

1. Zapisz oczekiwania wynikające z minimalnego workflow i ograniczenia origin. Zarejestruj nowy moduł `playwright_tests` w lib.rs; dodaj testy kontraktu launchera i lifecycle przed produkcyjnymi zmianami.
2. W fixture E2E utwórz dwa serwisy HTTP z syntetycznymi danymi. Pierwszy odpowiada 401 z `WWW-Authenticate: Basic` bez poprawnego Authorization; drugi jest innym origin i rejestruje otrzymane nagłówki. Nie zastępuj obsługi HTTP mockiem.
3. Nowy scenariusz zainstalowanego adaptera ma użyć osobnego świeżego projektu bez `reports`, `local.json` i dodatkowego env dla Basic Auth. Runner wewnątrz VM może nadać zbudowanemu obrazowi testowemu dodatkowy tag `ai-profiles-playwright:0.2.0`, aby nie wymagać local.json wyłącznie do podmiany obrazu. Publiczna nawigacja działa przy braku credentials. Serwery fixture uruchom przed zapisem credentials, aby wpisać rzeczywisty przydzielony origin. Po utworzeniu poprawnego pliku i restarcie MCP pierwszy origin odpowiada 200, drugi nie otrzymuje Authorization. Dane nie pojawiają się w discovery ani raportach. Zachowaj osobno istniejący scenariusz z local.json/env_file sprawdzający próby nadpisania metadanych adaptera — nie zastępuje on testu czystego uruchomienia.
4. Uruchom `make test` oraz `make test-playwright`. Uzasadniony RED: brak binarium w payloadzie/automatycznego reports lub niepodłączone credentials prowadzące do 401, a nie błąd infrastruktury czy kompilacji nieistniejącego importu. Minimalne deklaracje/stuby potrzebne do skompilowania testu są dopuszczalne; RED ma wynikać z asercji. Aby wyizolować RED autoryzacji, test może początkowo przygotować katalog i jawnie wybrać host networking, lecz końcowy scenariusz czystego startu nie może korzystać z tych ułatwień.
5. Dodaj minimalny launcher i dystrybucję; uaktualnij fixture zastępujące stare założenie „update usuwa launcher” nowym kontraktem zarządzanego binarium, zachowując ochronę obcych plików. Nie usuwaj zasadnych asercji w celu GREEN.
6. Wykonaj GREEN i `make test-all`. Zapisz wykonane testy, zmiany i ograniczenia w planie.

## Weryfikacja i oczekiwane wyniki

- Rust / tempfile: poprawny układ każdego z trzech klientów, uruchomienie niezależne od cwd, niezgodny projekt odrzucony, katalog reports utworzony raz, istniejące dane nienaruszone, plik/symlink reports odrzucony przed Dockerem; prywatny plik symlink/world-readable odrzucony, brak pliku domyślnego dozwolony, brak jawnie wskazanego niedozwolony.
- Składanie Compose: ręczny override obrazu zachowany, kolejność oryginalnych plików zachowana, brak duplikatu auth overlay, opcjonalny storage state nadal działa. Mock runner/spec jest dozwolony wyłącznie do inspekcji procesu, nie jako dowód działania MCP.
- Lifecycle: launcher tylko dla wybranego serwera, executable bytes/hash, brak źródłowego checkoutu w runtime; każdy klient dostaje własny adapter/launcher; update jednego nie rusza innego; lokalna modyfikacja zarządzanego pliku nadal blokuje update. Credentials i reports nie należą do mapy zarządzanych plików i pozostają po uninstall.
- Git: reguła dopisana bez utraty innych bajtów/komentarzy/CRLF i bez duplikatu; niepowiązany profil nie zmienia `.gitignore`. W scratch repo sprawdź rzeczywistym `git check-ignore --no-index .private/playwright-basic-auth.json`, że standardowy domyślny plik jest ignorowany. Nie używać prawdziwego HOME/repo użytkownika.
- HTTP: dyskryminujące asercje to rzeczywiste 200 zamiast 401 oraz brak Authorization na drugim origin, również po przekierowaniu. Zły port/hasło nie daje fałszywego sukcesu. Helper zachowuje normalizację origin i redakcję błędów.
- Prawdziwy zainstalowany adapter/launcher bez local.json i z cwd `/` musi przejść stdio, nawigację, axe i host-visible screenshot. Test samego skopiowania binarium nie wystarcza.
- Polecenia z root: iteracyjnie `make test`, `make test-playwright`; akceptacja `make test-all`. Zweryfikuj w wynikach nazwy nowych `playwright_tests`.

## Kryteria ukończenia

Publiczne użycie wymaga tylko builda i restartu; Basic Auth dodatkowo jednego pliku z trzema zaakceptowanymi polami. Nie potrzeba local.json ani ręcznego mkdir; wymagane testy przeszły, nie utracono izolacji klientów i ochrony sekretów.

## Warunki zatrzymania

Nieznana kolejność/semantyka overlay, potrzeba pominięcia origin, konflikt lokalnych plików, utrata sekretu/ochrony Git, nieoczekiwany błąd lub brak VM. Nie zgaduj danych logowania, nie wykonuj buildu/pull w launcherze i nie zmieniaj transportu MCP.
